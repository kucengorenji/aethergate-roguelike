# 0014: VFX in code (plan)

Spec: docs/specs/0014-vfx.md

## Approach

Effects are split the same way the game already splits simulation and presentation.

- **Emission is a cosmetic fixed system** (`vfxSystem`), registered after the rules and before `feedbackSystem`.
  It reads what happened this step (new impacts and arcs at age 0, a new `state.hits` queue, projectile slots that appeared, enemy state changes, statuses, hazards, the burning ring) and writes particles into a pooled struct-of-arrays (`ParticlePool`).
  Its randomness comes from `state.vfx.rng`, a second `Rng` seeded from the launch seed with a fixed salt, so `ctx.rng` and every gameplay outcome stay exactly as they are.
- **A particle stores only its initial conditions** (birth time on a cosmetic clock, position, velocity, drag, gravity, size, color, lifetime).
  Its position at any age is a closed-form function, so the fixed system never integrates particles: it spawns them and frees expired slots.
  The cosmetic clock advances by `ctx.dt`, so sparks hold still during hitstop like everything else.
- **Drawing is frame systems** that evaluate the pool, the projectiles, enemies and hazards at the interpolated time (`ctx.alpha`), so paused screenshots are deterministic.
  Sprites, trails and ash are camera-facing quads built on the CPU, so these systems run after `tpsCameraSystem` (like the damage numbers).
  Each kind of geometry is one instanced draw with a small TSL material: soft sprites, ribbons (trails, lightning, meteor tails), ground decals (telegraphs, rings), ice shells, meteor rocks, ash.
  Sprites and ribbons use premultiplied blending, so additive glows and alpha-blended smoke share one draw call.
- **Telegraphs are data.** A pure function turns enemy state, hazards, the burning ring and recent impacts into a list of decals (shape, position, size, rotation, progress, color); the renderer draws the list, and `inspect()` returns the same list for tests.
  The fill progress is the wind-up fraction (or the hazard countdown), so it reaches the rim exactly on the strike step.
  This replaces the per-enemy marker meshes and the old hazard renderer.
- **Post-processing lives in the engine** (`src/engine/post.ts`, game-agnostic): a `RenderPipeline` with the scene pass (MSAA as before), an optional `BloomNode` on the HDR scene with a luminance threshold, ACES output, then a display-space grade (gain, lift, saturation, contrast, vignette).
  Magic colors are pushed above 1.0 (HDR) by `glow` tunables, so only magic and wind-up eyes pass the bloom threshold.
  `Game.setRenderPass` swaps the plain `renderer.render` for the pipeline; the post frame step reads the quality setting each frame and rebuilds the output node only when bloom switches.
- **Bundle:** the game's entry chunk is at 43.6 of 60 KB and the HUD branch adds to it too, so the effects code is a lazily imported chunk (`src/game/vfx/index.ts`), started in parallel with the save and the character model and awaited before systems are registered. `BloomNode` lands in the cached `three` vendor chunk.

Cosmetic hooks in gameplay code are one-line pushes, like the existing `state.impacts`: hit marks from `applyDamage`, a cosmetic `look` on projectiles (staff, thorn orb), and named impact kinds with an optional radius (slams, meteors, spores).

## Risks

- **Software rendering in tests.** Bloom adds about a dozen small passes per frame in SwiftShader; paused tests only render on request, so the suite should grow by seconds, not minutes. Measure and report.
- **Backends.** The TSL materials and the post chain must compile on WebGPU and WebGL 2; the E2E suite runs one backend, so one test forces `?renderer=webgl`.
- **iGPU cost.** MSAA scene pass to a half-float target plus bloom at half resolution; Low drops bloom. The frame cost is checked with the debug overlay, not in CI.
- **Merge conflicts.** `index.ts` and `config.ts` are shared with the HUD branch: insertions only in the system chain, one new `vfx` block at the end of the config, and the `quality` presets extended in place.
- **Baselines.** Every visual baseline changes (grade, ash). They are recorded in the cloud and must be re-checked on Mikael's WSL machine.
